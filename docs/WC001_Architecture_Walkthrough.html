lifting-anchor-agent — architecture walkthrough

How the WC001 lifting-anchor agent actually decides

A proof-of-concept AI agent that places lifting anchors on a precast concrete wall panel. Every safety number is computed by deterministic engineering code; the AI is confined to one bounded decision — which catalogue anchor to try next — and cannot influence the final result even if it tries to.

element: WC001 4700 × 3000 × 180 mm STATUS: HOLD reason: geometry sources disagree

A

cli.py — where a run actually starts

Everything begins with one command: python -m liftagent run data/wc001.json. argparse (Python's standard command-line library) reads and validates what was typed — is there a JSON path? Is --reinforcement-confirmed exactly "true" or "false", not some other text? — before any of this project's own logic runs at all.

why it's built this wayRolling a hand-written argument parser would mean re-inventing validation, help text and error messages that a decades-old standard library already gets right. The same engineering instinct shows up everywhere else in this codebase: don't hand-roll something a well-tested tool already does reliably.
B

ingest.py — three geometry sources, one genuine disagreement

WC001's geometry doesn't arrive as one clean number — it arrives from up to three places, and this stage's job is to normalise each into a typed record and check whether they agree.

approval_design  4700mm, 2 openings   — the design drawing (authoritative)
ifc_export       4300mm, 0 openings   — a typed-in summary field (a claim, never re-parsed)
ifc_geometry     ~4700mm, unknown     — the real .ifc file, independently measured (optional, --ifc)

ifc_export and ifc_geometry look similar but mean different things: one is a written claim nobody verified, the other is this program actually opening the real IFC file and measuring its 3D geometry. Notably, the independently-measured value agrees with the design drawing (4700mm), not with the typed-in summary (4300mm) — evidence the summary field may itself be the stale one.

why the conflict mattersdetect_geometry_conflict() pairwise-compares every usable source's length (25mm tolerance) and, only when both sides reliably extracted them, their opening counts. Any disagreement beyond that tolerance means the system can never silently guess which number is correct — it flags a conflict and defers to a human.
C

agent.py — setup, before any anchor is tried

Two hard facts get established immediately, and both can independently force a HOLD later: is the geometry resolved (no conflict), and is the turn method — how the panel gets physically flipped from flat to vertical, on a supporting tilting table or by a rougher free crane lift — actually confirmed? WC001's input says "UNCONFIRMED".

not a guess, either wayEven with the turn method unconfirmed, the system doesn't skip evaluating it — it runs both the gentle table case and the conservative, rougher free-crane case, so a human has real numbers for either outcome. It still can't accept a result built on an unconfirmed input, though — passing a conservative check is not the same as a human actually confirming the real plan.
D

The agent loop — the only place AI can act, deliberately boxed in

For each catalogue anchor (up to 5, tried in a fixed capacity-based order), three things happen in sequence:

1. Reasoner — picks a name, nothing else

Its return type has exactly one field, anchor_type — structurally, there is nowhere to put a force, a capacity, or a status. MockReasoner (the default, fully offline) just walks the fixed list. LLMReasoner (only active if ANTHROPIC_API_KEY is set) asks a real model, but never trusts its raw reply — chosen = text if text in remaining else remaining[0].

2. Validator — a second, independent gate

Rejects any anchor name that isn't a real catalogue entry, before it's ever acted on. An adversarial test double, EvilReasoner, always names a fake anchor ("SUPER-ANCHOR-9000-NOT-IN-CATALOGUE") and always lies in its explanation text — proving the validator catches the fake name, and that a lie in explanation text can never reach an already-computed, frozen result object.

3. Evaluate candidate — the real engineering core

Self-weight (volume × density, not the brief's uncited 72.6kN figure), centre of gravity (net of openings), trial placement at 20.7% of the panel length from each end (the position that minimises bending), then every check: edge distance, axis spacing, wall thickness, opening clash, capacity per handling state, reinforcement confirmation, clutch match.

If the trial position fails edge distance, axis spacing, or opening-void clash, a single bounded "move in" search runs — a closed-form calculation of the smallest inward shift that clears all three requirements, never a stepped search. The result is always re-verified against the real, unchanged check functions before being trusted.

the determinism boundary, provenTwo independent Reasoner implementations produce byte-identical engineering numbers. A validator rejects any invalid or hallucinated action. An explanation can lie freely and it changes nothing, because the result was already computed and frozen before the explanation was ever written. This is tested under deliberate attack, not just assumed.
E

enforce_invariants() — the final, independent verdict

After the loop finishes, one function recomputes the status from raw facts only — never from anything the Reasoner said:

if not geometry_resolved:      return HOLD, "UNRESOLVED_GEOMETRY_CONFLICT"
if not turn_confirmed:         return HOLD, "TURN_METHOD_UNCONFIRMED"
if reinforcement != PASS:      return HOLD, "SUPPLEMENTARY_REINFORCEMENT_UNCONFIRMED"
if candidate_passed:          return ACCEPT_PROVISIONAL, None
if candidates_exhausted:      return REJECT, "NO_CANDIDATE_SATISFIES_REQUIREMENTS"

HOLD means "we don't have enough confirmed information to decide." REJECT means something stronger: every real option was tried, and the honest answer is none of them work. WC001 hits the very first line — the geometry conflict — so it correctly HOLDs, regardless of how the anchor math turns out.

F · G

RFIs, the audit trail, and the final report

The same raw facts that drove the status also drive the human-facing "please confirm this" messages (RFIs) — both are read from one shared source of truth, so they can never contradict each other. Every intermediate calculation is separately logged into a full rule_trace, whether or not it ended up mattering to the final status.

report.py turns the finished, immutable result into the structured JSON and a human-readable terminal summary; visualize.py draws the 2D elevation with the anchor positions. Even when the status is HOLD, the calculated placement still gets drawn and reported — clearly labelled "illustrative, not a resolved placement" — so a reviewing engineer isn't left with nothing to look at.

summary

The determinism boundary, in one place

The brief's central question was: where does the AI belong, and where must it never go? This architecture answers it with four independent, tested layers:

  1. Typed action space. The only thing an AI component can ever return is one anchor name or a give-up signal — never a number, by construction of the data type itself.
  2. A second, independent validator. Any illegal or hallucinated action is rejected before it can be acted on.
  3. An invariant guard. The final status is always recomputed from raw deterministic facts, and the AI's own opinion is never read.
  4. Immutability. Every result object is frozen the instant it's built — nothing downstream, including an explanation step, can reach back and change it.
honest limitations

What this POC doesn't do — on purpose

Only one position is ever tried per anchor.

The "move in" search is a single closed-form calculation, not an optimiser. It can only ever make the system more conservative — reject a candidate or escalate to a different anchor — never accept something unsafe.

Opening trimmer/3D reinforcement clash isn't modelled.

Landing an anchor right at the mathematical edge of a void isn't necessarily ideal in practice — real trimmer reinforcement around an opening isn't checked. Documented as an explicit next step, not silently assumed fine.

The supplied WC001 IFC doesn't provide extractable opening geometry.

The file's panel is proxy-style geometry, without the semantic wall/opening entities (IfcWall + IfcOpeningElement + IfcRelVoidsElement) needed to deterministically recover the two approval openings. The agent reports that opening information as UNKNOWN rather than inferring or fabricating it, contributing to WC001's geometry conflict and HOLD — a separate wall-modeled IFC file was investigated and confirmed this kind of extraction is feasible when the file does carry that structure, so this is a known input-format limitation, not a fundamental one.

Self-weight is derived, not copied from the brief's figure.

The brief's own "G = 72.6kN" doesn't reconcile with any geometry + density combination given. This system computes it from first principles (volume × density) and reports the brief's figure only as an unverified reference, never as an authoritative input.
